# BizOpt app audit — 16 October 2026

**Recommendation:** prioritize a reliability and security release, followed by a narrow private beta built around one working publishing channel. The current branch has useful foundations, but it should not be treated as ready for a public paid launch.

Audited branch: `feat/platform-experience`, commit `57f706c`. This assessment covers the local repository, automated checks, selected browser flows and dependency advisories. It does not establish the condition of any deployed production environment. Application source was not changed.

## Findings in priority order

### 1. P0 — Workspace mutations authorize after committing changes

**Evidence:** [workspace PATCH handler](../app/api/workspace/[id]/route.ts), lines 45–50, and [stage completion handler](../app/api/workspace/[id]/complete-stage/route.ts), lines 21–27. Both call the mutation service before comparing the result's `orgId` with the caller's workspace. The [service](../services/workspace/session.ts), lines 95–114 and 138–142, writes by session ID alone.

**Impact:** an authenticated caller who obtains another workspace session ID can change that record before receiving a forbidden response. A later HTTP 403 does not undo the database write. Request JSON is also passed directly into Prisma update data, allowing fields and nested operations beyond an explicit editor input contract.

**Next action:** authorize the existing record before every mutation; scope service reads and writes to the caller's workspace and the intended person/role policy; validate an explicit allowlist of editable fields and stage transitions. Commit the snapshot and stage update atomically. Add negative tests proving a foreign-workspace request leaves all records unchanged. This is a source-level finding; it was not exercised against any real tenant.

### 2. P0 — Registration and identity workflows fail on a PostgreSQL query

**Evidence:** [identity database helper](../services/identity/database.ts), line 10, uses `$queryRaw` to select `pg_advisory_xact_lock(...)` directly. PostgreSQL returns `void`, which the installed Prisma client cannot deserialize. Integration output reports `Failed to deserialize column of type 'void'`.

The browser reproduced a valid signup returning **HTTP 500**, with “This action could not be completed. Please try again.” See [signup screenshot](../.gstack/qa-reports/app-audit-2026-10-16/signup-result.png).

**Impact:** this helper is also used by identity rate counters and verification, recovery and account-security actions. Nine failing lifecycle tests include downstream failures caused by the first registration rollback; these are not nine independent root causes.

**Next action:** use a Prisma-compatible lock query and preserve transaction semantics. Existing billing services already use a supported `SELECT 1 AS locked FROM pg_advisory_xact_lock(...)` pattern. Re-run all database tests and the signup → verify → recover → sign-in journey before calling identity complete.

### 3. P0 — Known critical dependency advisories need remediation

`npm audit --omit=dev --json` reports 16 affected package entries, including four rated critical. Resolved versions include Next.js **15.5.18**, NextAuth **4.24.14**, `@auth/prisma-adapter` **2.11.2** and its `@auth/core` **0.41.2** dependency.

Upstream confirms a critical [Next.js image optimization advisory](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4) and an [Auth.js email normalization advisory](https://github.com/nextauthjs/next-auth/security/advisories/GHSA-7rqj-j65f-68wh). Applicability depends on the feature and deployment: package-level audit ratings are not proof that every advisory is exploitable through this application's configured credentials flow. Transitive affected entries can reflect the same underlying advisory.

**Next action:** update compatible patched versions and the lockfile, inspect remaining transitive findings, and re-run auth, image, build and database checks. Do not blindly apply a forced major upgrade or describe the advisory count as independent successful exploits.

### 4. P0 for the advertised product — Social publishing reports simulated success

**Evidence:** [LinkedIn](../services/platforms/linkedin.ts), [TikTok](../services/platforms/tiktok.ts) and [Meta](../services/platforms/meta.ts) publish methods return success with timestamp-based IDs without calling a provider. A local invocation using an invalid token and nonexistent account returned success for LinkedIn, Instagram and TikTok.

The [OAuth callback](../app/api/social/callback/route.ts) constructs an account ID from the authorization code and does not exchange the code for usable access tokens. The [publish worker service](../services/publishing/index.ts), lines 55–62, then records the connector result as published. This conflicts with the landing page's “posts go live via official platform APIs” promise.

**Next action:** clearly gate simulated connectors, then complete one real provider: OAuth exchange, encrypted token storage, expiry/reconnection, actual publishing, provider confirmation and a link to the resulting post. LinkedIn member publishing is a reasonable first candidate already represented in the code, subject to the approved target account type and [required platform permissions](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin). Hide unsupported channels from the live publishing promise until verified.

Also fix the delivery boundary before relying on it: scheduling currently lacks an idempotency constraint and transaction across campaign/posts; `retryPost` can requeue a published post; a worker crash after claiming a post has no publishing lease recovery; and `processDuePosts` does not supply campaign media to the connector. These create duplicate, stuck or incomplete posts once real publishing is introduced.

### 5. P1 — Media storage is incompatible with the documented Vercel deployment

**Evidence:** [storage implementation](../lib/storage.ts), lines 15–38, writes to `process.cwd()/storage/private-uploads`. Selecting S3 throws “S3 upload is not configured yet.” The media library nevertheless describes S3-compatible storage as available.

**Impact:** the documented deployment cannot provide durable uploaded assets with this implementation. [Vercel Functions use a read-only filesystem with temporary scratch space](https://vercel.com/docs/functions/runtimes#file-system-support).

**Next action:** implement private durable object storage and authorized downloads, verify asset persistence across instance/release changes, and provide provider-appropriate media delivery. Keep storage capability text aligned with the implementation.

### 6. P1 — Release checks and database setup are incomplete

- [CI configuration](../.github/workflows/ci.yml), line 56, contains `use:` rather than the required action step key `uses:`. This is invalid against [GitHub's workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsuses); actual remote workflow status was not inspected.
- CI does not provision PostgreSQL or set the explicit test datasource variables, so its default test command skips the 35 database tests that revealed the identity defect. Browser scripts are not part of the ordinary test command.
- The existing disposable database lacks earlier phase 2.1 columns/tables required by the current Prisma client. `/home`, `/growth-intelligence` and `/compliance-center` rendered error boundaries for missing `GrowthPrediction.confidence` / `ComplianceCheck.explanation`. This establishes a test-environment migration gap, not that a production deployment has these errors.
- A read-only Prisma schema comparison also proposes dropping a manually added notification tenant foreign key. Consequently, blindly using `prisma db push` to repair drift can remove protections not represented in the Prisma model. The diff was saved for inspection and **was not applied**.
- `.env.example` omits required identity/notification settings such as explicit `APP_URL` and `NOTIFICATION_PAYLOAD_KEY`, while the account-lifecycle and email runbooks require them. A documented quick start does not currently describe the whole running system.

**Next action:** establish one tested migration/seed path from an empty database, preserve SQL-level tenant constraints and RLS, repair the workflow, and make database/security regression tests required. Keep a staging smoke test for real rendered content; HTTP 200 alone missed the error boundaries.

### 7. P1 — Background automation still needs an operational deployment

Workers for outbox dispatch, notification delivery/reconciliation, publishing and billing reconciliation run a tick and exit. The repository's Vercel configuration does not schedule them. External schedulers might exist, but none were verified. Some newer worker wrappers are also absent from package scripts.

**Impact:** queued work can remain queued even while the website is available. Publishing's claim handling is less resilient than the leased outbox/notification queues.

**Next action:** deploy independent managed worker/scheduler processes with startup configuration validation, restart behavior and queue-age/failure alerts. Demonstrate delivery through a restart and webhook retry. Validate provider delivery and Stripe test-mode lifecycle flows in staging before enabling paid changes.

The parallel database run additionally hit an invitation `P2034` transaction conflict; that suite passed alone and serialized. Add bounded serialization retries where appropriate and preserve seat/idempotency invariants under contention.

### 8. P2 — Product feedback can imply evidence that does not exist

**Observed:** a fresh workspace's analytics page displays success rate `100` with zero posts. [Analytics](../services/analytics/index.ts), lines 36–39, deliberately defaults to 100. [Growth scoring](../services/growth/scoring.ts) uses that default and subscription status in a growth score; predicted reach and engagement are formulas, not measured audience outcomes. An empty compliance history defaults to `pass`.

**Next action:** show “No data yet” / “Not checked” until evidence exists. Label estimates as heuristics and state the inputs. Keep actual provider metrics separate from app activity. The SEO provider descriptions already offer a useful pattern by distinguishing manual and unavailable features explicitly.

## Product and UX recommendation

The component system, typography, reusable form/error primitives, service boundaries, tenant-aware newer services and durable notification design give the project a useful base. The primary issue is that the product promise extends beyond the proven execution paths.

The navigation currently exposes 16 destinations. Make the first customer outcome explicit:

**Create an account → generate and edit a useful content pack → connect one supported account → schedule → see a provider-confirmed published post.**

Keep advanced growth/compliance/SEO areas secondary until a customer has completed that journey. Distinguish ideas, templates, external AI generation and measured results. Replace the marketing hero's illustrative dashboard with a current product screenshot or clearly identify it as an illustration. Keep the introductory charge and recurring price understandable together at the first CTA.

After the blockers are resolved, run a small private beta with a suggested initial cohort of 5–10 businesses from one segment. Measure time to the first useful draft, time to first confirmed post, publish success, week-two return and trial-to-paid conversion. Treat these as proposed measurements, not existing analytics or guaranteed targets. Review actual AI/provider/storage/support costs before promising unlimited usage at the current price.

## Suggested execution sequence and exit criteria

1. **Restore safe access.** Fix workspace authorization/input boundaries and identity locks; update vulnerable dependencies. Exit when all 420 existing tests pass with no database skips and foreign-workspace writes are proven to leave no changes.
2. **Make releases reproducible.** Repair CI; migrate and seed a fresh staging database; validate required settings; deploy workers and durable storage. Exit when staging pages render their intended content and queued work survives restarts.
3. **Prove the core outcome.** Complete one provider and publishing recovery/idempotency, then exercise registration, verification, Stripe test-mode access, scheduling, actual test-account publishing, failure/retry and cancellation. Exit when a post is confirmed by the provider and duplicate/replayed requests do not create another post or charge.
4. **Observe the private beta.** Add focused onboarding and measure activation/return behavior before expanding connectors or intelligence features.

## Coverage limits and artifacts

Browser signup failure is reproduced; workspace cross-tenant mutation is established from source order and selectors rather than an attack against a deployed service. Public marketing, signup/login and selected authenticated screens were inspected. Pricing fit 320px without horizontal overflow. SEO/workspace were captured in loading states, so their functional completion is unverified in this audit. Billing navigation timed out, and later settings/support/mobile checks were not completed. Local free disk was approximately 453 MiB; no production performance conclusions are drawn from this development run. Safari, Firefox, assistive technology and physical devices were not tested.

Evidence is saved locally under [the audit artifact directory](../.gstack/qa-reports/app-audit-2026-10-16/): browser results, screenshots, full/serialized test logs, dependency audit JSON and the unapplied schema diff. No single numerical readiness score is assigned: passing static checks cannot offset blocked registration, missing real publishing or an authorization flaw.
